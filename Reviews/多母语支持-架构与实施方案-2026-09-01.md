# 多母语支持 — 架构与实施方案

日期：2026-09-01
状态：**草案 — 待产品负责人确认，未授权实施**

背景：为上架做准备，目标用户是真正生活在瑞典的移民（阿拉伯语、英语、索马里语、乌克兰语等群体），中文用户只是很小一部分。参考你提供的优先级列表：P0 = 英语、阿拉伯语、中文（已有）、乌克兰语、索马里语；P1 = 波斯语、波兰语、俄语、西班牙语、土耳其语。

---

## 一、先核对现状：哪些内容跟"母语"绑定，哪些不绑定

查了 `learning_objects` 表的真实字段（10096 个词 + 843 个 Fraser/Uttryck，共 10939 条）。结论很重要，直接决定工作量：

**跟母语绑定、需要为每种新语言重新生成的字段**：
- `chinese`（中文释义）
- `example_zh`（例句中文翻译）
- `memory_tip` / `grammar_note` / `meaning_note`（记忆提示、语法备注，目前是中文长文本）
- `collocations` / `related_words`（这两个是一整段扁平文本，瑞典语短语和中文释义写在一起，比如"arbeta som webbdesigner | 担任网页设计师工作"——中文是嵌在文本里的，不是单独字段）

**跟母语完全无关、所有语言的学习者共用同一份、不需要重做的字段**（这是大头）：
- `swedish`、`lemma`、`example_sv`（瑞典语原文和例句）
- `forms`、`ipa`、`pos_detail`、`cefr_level`、`frequency_rank`、`frequency_band`
- `countability`、`transitivity`、`comparison_type`、`passiv_s`、`function_tags`（语法分类，跟语言无关，只是显示时套一层翻译）
- `swedish_explanation`（瑞典语解释）
- `learning_object_collocations`（搭配的结构化短语文本本身）、`learning_object_relationships`（词与词的关联关系）

也就是说：真正需要为每种新语言重做的，是"用这种语言解释这个瑞典语概念"这部分内容，不是整个词条。这大大降低了每加一种语言的实际工作量——但仍然是真实、不小的工作量。

## 二、架构方案：新增一张"翻译表"，不改动现有列

不建议给 `learning_objects` 表每种语言加一列（`chinese`、`english`、`arabic`……），那样每加一种语言就要一次数据库迁移，长期不可持续。

改成一张独立的翻译表：

```sql
create table learning_object_translations (
  id uuid primary key default gen_random_uuid(),
  learning_object_id uuid not null references learning_objects(id),
  language_code text not null,  -- 'zh', 'en', 'ar', 'uk', 'so' ...
  translation text,             -- 对应 chinese
  example_translation text,     -- 对应 example_zh
  memory_tip text,
  grammar_note text,
  meaning_note text,
  collocations text,            -- 整段搭配+释义文本，按语言各一份
  related_words text,
  created_at timestamptz default now(),
  updated_at timestamptz default now(),
  unique (learning_object_id, language_code)
);
```

现有的中文内容（`chinese`/`example_zh`/`memory_tip`/`grammar_note`/`meaning_note`/`collocations`/`related_words`）**零 AI 成本**地搬进这张表，作为 `language_code = 'zh'` 的一批行——纯数据迁移，不用重新生成。`learning_objects` 表原来的这几列可以先保留做兜底（如果翻译表里某个语言的某个词还没翻译，就显示中文，不留空白），等以后确认稳定了再考虑清理，不急着这次就删。

前端读取逻辑：从"直接读 `word.chinese`"改成"读 `translations[用户选择的语言] ?? translations['zh']`"——一处改动，所有渲染词卡的地方复用。

用户的"母语"选择存在 `user_preferences`，跟现在 `favoriteCategory`/`dailyNewWordTarget` 一样的存法，不需要新表。

## 三、这次的真实工作量比想象中大——三块要分开看

1. **词库内容翻译**（上面说的这张表）——这是核心，但只是三块里的一块。
2. **阅读模块（Läsning）**：文章的 Sammanfattning、重点单词释义、Fraser & Uttryck 都是**每次分析时实时用 AI 生成**的，不是固定词库，机制不一样——不是"翻译已有内容"，而是"分析时直接告诉 AI 用哪种语言生成"，这个成本反而更低（分析本来就要花一次AI调用，只是提示词里加一个语言参数），但意味着阅读模块的多语言支持是另一套独立的改动，不能和词库翻译共用一次工作。
3. **App 界面本身的文案**（按钮、导航、提示语，比如"Repetera ord"、"Lägg till"这些）——现在全部是硬编码的瑞典语/中文混合文本，散落在 `index.html`/`app.js` 几千处。要让界面本身也讲用户的母语，需要先把这些文案抽成一套"翻译key"系统（这本身就是一次不小的重构），然后才谈得上翻译。**这一块我建议明确排除在这一轮之外**——学习者能接受"界面是瑞典语/英语，但词的解释是我看得懂的语言"，这是市面上语言学习app的常态（Duolingo 界面语言和目标语言解释语言也是分开管理、分阶段做的）。

## 四、阿拉伯语的一个额外硬性问题：从右到左（RTL）排版

阿拉伯语是从右到左书写的语言。现在整个 App 的 CSS 是纯从左到右（LTR）设计，没有做任何 RTL 适配。给阿拉伯语用户看的界面，如果词的中文释义位置全改成阿拉伯语但排版还是从左到右，阅读体验会很奇怪甚至混乱。这是一项独立于"翻译内容"之外的真实前端工程工作，不是加一个语言包就能解决的。

## 五、这次应该翻几种语言？——建议先做一种，验证清楚再批量

参考你之前审核中文内容时暴露的问题（AI生成的内容你自己看不懂瑞典语原文，只能靠流程和抽查信任结果）——这个风险在英语上是可控的（你自己能读英语，能亲自抽查质量），但阿拉伯语、乌克兰语、索马里语你完全不懂，翻译对不对、语气合不合适、有没有明显错误，你没有能力自己判断，只能完全依赖 AI 的自我审核，风险比中文那次更高。

**建议**：这一轮先只做**英语**（P0 里你能亲自验证质量的那个），把整套架构（翻译表、前端读取逻辑、语言切换入口）跑通、真实成本和质量都验证过之后，再批量做阿拉伯语/乌克兰语/索马里语——到时候可以考虑增加一道"找母语者抽查"的人工验证环节，而不是完全靠自己判断看不懂的语言。

## 六、成本预估（基于这次审核4646词时的真实单价，不是拍脑袋）

翻译比原创生成便宜（已经有瑞典语原文+中文释义做参照，不是从零创作），但仍是真实开支：

- 词库核心翻译（chinese/example_zh/memory_tip/grammar_note/meaning_note，一次AI调用整合完成，10939条）：预估约 $60-90（每条约 $0.006-0.008，参考之前审核阶段的实际单价）
- 搭配/关联词翻译（collocations/related_words，内容更长）：预估约 $40-60
- **单个语言合计：约 $100-150**（不含阅读模块和界面文案，那两块不是一次性成本，是持续按使用量计费/另立工作量）

## 七、决策清单

1. **架构**：新增 `learning_object_translations` 表、现有中文内容零成本搬进去，这个方案可以吗？
2. **这一轮范围**：先只做英语一种（推荐），验证完再批量做剩下的 P0 语言，还是你想直接一次性做完 P0 全部 5 种？
3. **阅读模块和界面文案**：这次明确不做，作为独立的后续工作——同意吗？
4. **质量把关**：如果以后做你不懂的语言（阿拉伯语/乌克兰语/索马里语），要不要在流程里加一道"找母语者抽查"的步骤？现在可以先不定具体怎么找人，只是想确认这个方向你是否认可。
