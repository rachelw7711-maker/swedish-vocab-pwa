## 2. Bug 与逻辑问题（实测发现）

### 2.1 首页"今日任务"数字短暂归零（P1）— **RESOLVED**（commit `c49e5da`，已验证部署）

> 按最简方案修复：保留 2800ms 兜底计时器，静态占位文案从"0 ord idag"改为"…"，`renderStudyStats()` 增加 `!state.dailyProgress` 早退出判断，避免用默认值覆盖占位文案。本地/生产均验证：刷新后先显示"…"，几秒后被真实数字替换，不再出现"0 ord idag"误导性文案。

**问题**：刷新首页或重新登录时，"Repetera ord"和"Lär dig nya ord"卡片会先短暂显示"0 ord idag"，工作量提示横幅（"今天复习比平时多，新词减少到 5"）也短暂消失，几秒后才被真实数字替换。

**原因**：`app.js:421-427` 有一个硬编码 2800ms 的兜底计时器——如果应用初始化超过 2.8 秀还没完成，就强制把 `document.body.dataset.appReady` 设为 "ready" 并展示应用外壳（此时首页用的是 state 里的默认/占位值，不是真实计算结果）。本地开发环境和真实登录会话下，初始化稳定超过 2.8 秒，兜底计时器每次都会触发（console 反复打印同一条警告 `Startup fallback: showing app shell after a slow or blocked init.`），这不是一次性巧合。

**影响**：用户刷新页面或较慢网络下打开 App 时，会先看到"今天没有任务"的错误印象，可能造成困惑或误以为学习进度丢失；如果用户在这几秒内就点击"Börja lära"，具体会走到哪条代码路径未深入验证，存在潜在的用较早/错误状态发起学习会话的风险。

**最简单方案**：不要改动 2800ms 兜底本身（它是为了避免加载失败时白屏，是合理的保护机制），而是让"Repetera ord"/"Nya ord"这两个数字卡片在真实数据到达前显示骨架屏/loading 占位（比如短横线），而不是显示误导性的 "0"。这是一个局部渲染改动，不涉及数据层。

**修改成本**：低（几十行内的前端改动，无需动数据库/接口）。

**是否建议执行**：建议，且优先级较高——这类"看起来没有任务"的错觉直接影响用户对 App 可靠性的信任感。

## 3. 安全问题（本次审计重点，均"发现问题→记录方案"，未自动修改）

以下 3 项因涉及"安全风险/接口行为变更"，按任务要求**只记录、不自动修改**，需要你确认后再排期：

### 3.1 `api/generate-word.js` 完全没有身份校验（P0）— **RESOLVED**（commit `2aa2b96`，已验证部署）

> 完全按建议方案执行：复用 `api/reading/analyze.js` 的 `readUserId` 鉴权模式（新增到 `api/generate-word.js` 和 `server.mjs` 本地路由），前端 `fetchGeneratedWord` 改为携带真实 access token。生产环境 curl 验证：未登录请求现在返回 401，此前是直接触发付费 OpenAI 调用。

**问题**：任何知道这个 URL 的人都可以直接 POST 任意"单词"，触发一次真实的付费 OpenAI 调用（且用了较贵的 `web_search` 工具调用模式），没有任何频率限制、长度限制或登录校验。

**原因**：`api/generate-word.js:11-28` 只校验了 `word` 是非空字符串，随后直接调用 `server-words.mjs:50-104` 的 `generateWord()`，未经过其他端点（如 `api/reading/analyze.js`）已经在用的 `readAuthenticatedUser()` 校验。这是 memory 里早前就记录过的已知缺口，本次确认**至今仍未修复**，且是生产环境真实存在的开放端点，不是"仅本地"的问题。

**影响**：被恶意爬虫/脚本发现后可无限次触发付费调用，直接对应 OpenAI 账单风险；由于当前是单用户测试阶段流量很小，实际发生概率不高，但一旦这个 URL 被搜索引擎/爬虫抓到就会成为真实成本。

**最简单方案**：给这个端点加上和 `api/reading/analyze.js` 一样的 `readAuthenticatedUser()` 校验，未登录用户直接拒绝。

**修改成本**：低（复用已有的鉴权函数，几行代码）。**是否建议执行**：强烈建议，且应优先处理——这是本次审计里唯一真正的"真金白银"风险项。

### 3.2 `api/shadowing/tts.js`（以及本地开发中 `server.mjs` 的重复实现）鉴权是"有 token 才查，没 token 就当匿名放行"，且没有文本长度上限（P0）— **RESOLVED（方案与原报告建议有出入，已记录原因）**（commit `2aa2b96`，已验证部署）

> **执行时发现报告原文的判断与实际代码不符**：这个端点不只是 Shadowing 专用——`app.js` 的 `speakSwedish()`（也就是 Ordbok 里每张词卡"Lyssna"发音按钮背后的实现，全应用最高频的功能之一，未登录/已登录用户都在用）复用的正是这同一个端点，且设计上就是不带 token 调用的。如果照原方案"没 token 一律 401"，会直接打断全站发音功能。按任务要求"以实际代码和测试结果为准，并记录原因"，调整为：**只加文本长度上限（20000 字符，对齐阅读分析模块），不强制要求登录**——这样既堵住了"无限制长文本触发付费 TTS"的真实成本风险，又不破坏"Lyssna"这个核心功能。生产环境验证：匿名短文本请求仍正常返回 200（发音功能不受影响），超长文本请求正确返回 400。

**问题**：这个端点会在没有 `Authorization` 请求头时静默以 `user = null` 继续执行，而不是直接拒绝——也就是说未登录用户同样可以触发真实的 Azure/ElevenLabs 语音合成付费调用。而且和阅读分析接口（限制 20000 字符）不同，这里**没有任何文本长度上限**，理论上可以提交任意长的文本。

**原因**：`api/shadowing/tts.js:170-193, 208-273`（本地开发环境 `server.mjs:229-257, 303-434` 是一份几乎逐行相同的重复实现，见第 4.1 节）里的 `readUser()`/`readAuthenticatedUser()` 只在检测到 Authorization 头时才校验，缺失该头时直接放行，不像其他端点那样在缺失时返回 401。

**影响**：同样是真金白银的成本风险，且因为没有长度上限，单次调用的潜在成本上限比 3.1 更高。

**最简单方案**：改为未提供 token 时直接返回 401（和其余阅读类端点保持一致的鉴权行为），并给 `text` 字段加一个合理的最大长度校验（比如与阅读分析一致的 20000 字符）。因为这处逻辑在 `server.mjs` 里被复制了一份，两处都要改（正好可以借这次机会做 4.1 节提到的合并，一次到位）。

**修改成本**：低到中（逻辑简单，但因为有两份重复代码，工作量翻倍——这也是为什么 4.1 节建议先合并再修）。**是否建议执行**：强烈建议，与 3.1 同等优先级。

### 3.3 `api/promote-collocation.js` 没有任何身份/角色校验，任何人都能往公共词库里写入内容（P1）— **RESOLVED**（commit `2aa2b96`，已验证部署）

**修改成本**：低。**是否建议执行**：建议，可以和 3.1 一起顺手做，优先级略低于两个付费调用端点，但同样不建议长期搁置。

## 6. GitHub 同类优秀开源项目对比

### 6.1 最相关的项目

**Lute v3**（LuteOrg/lute-v3，约 670 star，MIT，Python/Flask，活跃维护）——经典 "Learning With Texts" 工具链的现代继承者，是 Läsning 模块最直接的开源对标。核心交互是"边读边点词查释义"（inline click-to-gloss），而不是像 Läsning 现在这样"先分析整篇文章，再看报告"。它没有任何 AI 生成步骤，词典数据来自通用在线查询，谈不上你们的 CEFR 分级/成语提取/成本缓存这些能力，但"边读边查"这个交互思路本身值得借鉴——完全可以在现有的分析报告之上，叠加一层轻量的"点词查释义"（复用已有的 DB-first 缓存架构，不需要新的 AI 调用）。原版 LWT 项目的维护者本人已明确表示逐步转向 lute-v3。

**FSRS / ts-fsrs**（open-spaced-repetition 组织，ts-fsrs 约 746 star）——用难度/稳定性/可提取性三个隐变量拟合每张卡片的记忆曲线，取代了 1987 年设计的 SM-2 系固定间隔算法。2024 年起已成为 Anki/AnkiDroid 的默认或可选调度算法。**需要明确指出的限制**：FSRS 要求每次复习有明确的四档评分（again/hard/good/easy），而 SpråkLab 目前的评分是从拼写测试尝试次数反推出来的（一次答对=good，多次答对=hard，用完机会=again）——直接套用 FSRS 前，需要先决定要不要把这个隐式评分机制改造成更接近显式评分的形式，这不是一次简单的算法替换，值得单独立项评估，而不是本次顺带做。

**Anki / AnkiDroid** —— 作为 SRS 产品的参考基准，价值主要在 UX/架构先例（显式评分按钮、按牌组的新词/复习量控制），而不是直接的功能对标对象。

**flashcards-open-source-app**（kirill-markin）——一个较新的、把 FSRS 调度和 LLM 辅助卡片生成结合起来的项目，是"AI 生成内容 + 现代 SRS + 多端"这个组合思路里最接近 SpråkLab 定位的对标，但从代码看它似乎是"每次编辑都实时调 AI"，没有看到类似你们 DB-first-before-AI-call、跨用户复用缓存分析这类成本控制架构——这恰恰是本次调研里 SpråkLab 相对最明显领先的地方（见 6.3 节）。

**Kaikki.org / Wiktextract**——机器可读的 Wiktionary 抽取管线，是构建词典功能常用的开放数据源，但瑞典语在其目前公开支持的"独立语言版"列表里**没有被确认覆盖**（已确认覆盖的包括德语/法语/西语/俄语/中文/日语/波兰语），瑞典语相关内容更可能只存在于英文 Wiktionary 对瑞典语词条的记录里，覆盖度和结构化程度都更弱。

**Folkets Lexikon（KTH）及其周边小工具**——经典的开放瑞典语-英语词典数据集，本身可用，但围绕它的 GitHub 小工具（CLI 查询、格式转换）大多是小众、长期未更新的个人项目，**没有一个活跃维护的现代学习类 App 建在它上面**——这是本次调研里最明确的一条信号：瑞典语专属的开源学习工具生态非常薄弱。

**SpeechShadowing（Dthurow）**——和 Shadowing 模块做的事情字面意义上一样（播放原声、录音、对比），但只是一个没有 TTS 生成/字幕同步/SRS 集成的桌面 Python 小工具，star 数个位数，早期阶段项目。这也说明"跟读练习"这个细分赛道，开源世界目前基本没有成熟对标——不是 SpråkLab 做得不够好，是这个方向本来就少有人做。

### 6.2 成熟开源工具普遍具备、SpråkLab 目前还没有的能力

- **边读边点词查释义**（Lute/LWT 的核心交互）——比"分析整篇文章出报告"更轻量，可以叠加在现有 Läsning 报告之上，复用已有缓存架构，不需要额外 AI 调用。
- **真正的记忆模型调度算法**（FSRS）——比固定间隔阶梯更能按"这个词对这个人到底有多难"个性化调整复习节奏，但需要先解决评分信号的问题，建议作为独立评估项，不建议在本轮顺带引入。
- **一套开箱即用的起步阅读素材库**——Lute/LWT 生态通常配一批公开阅读材料，方便新用户"第一天就有东西可读"；Läsning 目前完全依赖用户自己粘贴/拍照导入文本，冷启动门槛偏高。

### 6.3 SpråkLab 已经领先或持平于这些项目的地方

- **词卡内容的丰富度和结构化程度**：Lute/LWT、Folkets Lexikon 提供的都是"一个释义+可能一个例句"级别的信息，没有任何一个开源项目在做你们这种 CEFR 分级、词频排序、搭配/近反义词/词族关联、记忆提示的完整结构化内容——这是本次调研里最扎实的一条"你们已经比它们强"的结论。
- **成本可控的 AI 架构**：先查数据库缓存再决定要不要调 AI、SHA-256 文本哈希去重、跨用户复用同一篇文章的分析结果——这套"生成一次、永久复用"的纪律性，在调研到的对标项目里（包括最接近的 flashcards-open-source-app）都没有看到同等程度的实现，是一个真实、可以对外讲述的差异化优势，不只是"锦上添花"。
- **单一贯通的学习链路**：开源世界里阅读工具（Lute）、SRS 引擎（Anki）、跟读工具（SpeechShadowing）是三个完全独立的项目，没有一个项目同时把"阅读→提取生词/短语→跟读→加入复习"串成一条链路。SpråkLab 在移动端把这条链路做通了，这本身就是架构上的领先，即便单看某一环节的成熟度不如专精工具。
- **面向用户的 AI 成本仪表盘**：调研到的项目都没有向终端用户展示"这个月用了多少 AI 额度、真实花了多少钱"，Profil 的 AI-användning 卡片更接近 SaaS 产品的做法，而不是典型开源工具的做法。

**调研口径说明**：瑞典语专属的开源工具生态确实单薄——本次找到的强对标项目（Lute、FSRS、Anki）全部是语言无关的通用基础设施，不是针对瑞典语的竞品，如实说明这一点，而不是把冷门/停更的小项目包装成"竞争对手"。

## 7. SpråkLab 的产品竞争力分析

**当前最大的优势**：词卡内容的深度和结构化程度，叠加成本可控的 AI 生成/复用架构。这两者叠加在一起，意味着 SpråkLab 有能力在保持极低边际成本的前提下持续产出高质量内容——这是开源工具做不到、多数同类商业产品也未必做到（它们通常要么内容浅、要么每次调用都真金白银）的组合。

**与同类产品相比缺少什么**：(1) 阅读时的"点词即查"轻量交互，目前是"整篇分析出报告"的重模式；(2) 真正个性化的记忆调度算法（目前是固定阶梯，不是千人千面）；(3) 面向新用户的起步阅读素材，冷启动依赖用户自带文本。

**哪些功能实际上没有必要增加**：不建议在当前单用户/预发布阶段投入的方向——多语言前端框架（`native_language` 参数化设计已经为未来预留好了，不需要现在动）、正式的 Credits 限额强制执行（记录机制已就绪，强制执行等真实多用户流量出现后再做）、管理员/审核角色体系（等 promote-collocation 真的开放给非你本人使用时再建，现在只需要一个"已登录"的最低门槛）。这些都是"已经为未来铺好路，但现在做就是过度工程"的典型例子，符合你自己一贯的判断("不要为未来还没到来的规模先建基础设施")。

**哪些地方最值得完善**：46% 的 AI 生成内容仍未人工复核——这不是代码问题，是运营/内容层面的真实积压，值得你评估是否要在 App Store 上线前把这个比例降下来，或者至少确认"AI，未审核"标签本身对早期用户是否会造成信任顾虑。

**用户为什么会选择 SpråkLab**：内容深度（不是随手一个释义，是完整语法/搭配/记忆网络）+ 一条从"读文章"到"学单词"到"开口跟读"到"隔天复习"全部打通的链路，这在瑞典语学习这个细分领域里目前找不到直接对标。

**如果下一阶段只能开发 3 个功能，应该开发什么**：
1. **阅读页面的"点词即查"轻量交互**——成本最低（复用已有缓存架构，几乎不产生新 AI 调用），直接对标本次调研里发现的最成熟开源模式（Lute），能显著降低 Läsning 的使用门槛。
2. **首页任务数字的加载体验修复**（本报告 2.1 节）——不是新功能，但直接影响每次打开 App 的第一印象，修复成本低、收益直接。
3. **安全加固三件套**（3.1/3.2/3.3 节的鉴权补齐）——不是"功能"，但决定了 App Store 上线后是否会真的产生非预期账单或内容污染，优先级应该高于任何新功能。
