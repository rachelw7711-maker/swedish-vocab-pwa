# SpråkLab 项目评估报告 — 我的理解与专业建议

这份文件用中文写给你看，是我把之前做的四份英文审计文件（现状审计 × 3 + Gap Analysis）整理消化后，用自己的话说清楚：**这个项目现在是什么样、问题出在哪、以及最重要的——你想做的"多母语支持"该怎么落地**。

这是我的专业判断，不是最终结论。看完之后如果你觉得哪里理解得不对，请直接告诉我，我们对齐了之后再决定怎么改。

---

## 一、SpråkLab 现在到底是什么

先说实话：**这是一个能正常运行、单人开发规模的手机端瑞典语词典 + 学习工具**，还不是一个"多语言学习平台"。这不是批评，是准确的定位——知道自己现在站在哪里，才能判断下一步怎么走。

技术上，整个应用是一个 9000 多行的原生 JavaScript 文件（没有用 React/Vue 这类框架，也没有构建工具），配合一个 Supabase 云数据库。已经能正常用的功能包括：查词典、背单词、每日学习和复习、跟读练习（Shadowing）。这些功能本身做得不错，跑得通，用户数据也在往云端存。

但是，"书架"里的阅读、视频两个模块，点开全是空的，只是两张带"即将推出"标签的卡片；短语（Fraser）、表达（Uttryck）这两个你规划里的重要模块，现在在代码里连影子都没有——只是"词性下拉菜单里的一个选项"而已。也就是说，你规划文档里已经写好的很多东西，代码进度其实远远落后于规划。**这本身不是问题，是正常的（规范先行是对的），但你需要清楚这个落差有多大。**

---

## 二、我认为最需要关注的几个问题

我不打算把几十条发现都列一遍（那份英文详单已经有了），这里只挑我认为真正重要、会影响你下一步决策的几件事。

### 1. 最优先：云同步失败是"静默"的，用户完全不知道

这是我认为**唯一一个应该立刻处理、不能拖**的问题。现在如果用户编辑一个单词、完成一次学习，数据同步到云端失败了，界面上**什么提示都没有**，只在浏览器开发者工具的日志里留一行记录——用户完全没办法知道自己的学习进度到底存上了没有。

你的产品定位是"帮助学习者长期积累、成长可追溯"，如果连"我今天的学习到底存没存住"都无法确认，这会直接动摇用户对这个产品最核心的信任。这个问题工程量不算大，但优先级应该排第一。

### 2. 导航结构是照着"一个词典 app"设计的，不是照着"一个学习平台"设计的

现在底部只有 3 个入口：首页、书架、我的。书架里挂着 4 张卡片（词典/跟读/阅读/视频）。这个结构对一个功能单一的词典应用来说是够用的，但你规划里至少还要加短语、表达、AI 老师这几个新模块——**现在的结构完全没有为它们预留位置，只能不停地往"书架"这个抽屉里塞卡片**。

这是我认为**第二重要**的问题，因为这类"骨架级"的决定，越往后拖，改动成本涨得越快——现在改是"调整设计"，等做完 5 个模块之后再改，就是"大手术"。

### 3. 界面从来没有一套统一的视觉系统

这个项目写了将近 5500 行 CSS，但字号用了 50 多种不同的数值、字重（粗细）用了 26 种不同的数值——正常一个成熟系统大概只需要 6-10 种字号、4-5 种字重就够了。这说明这些年一直是"每个新页面照着感觉写一遍"，而不是"照着一套标准写"。

这不只是审美问题，还牵出两个真实的可用性问题：
- **主按钮（app 里用得最多的那种绿色按钮）上的白色文字，跟按钮底色的对比度不够，不满足最基本的可读性国际标准（WCAG AA）**——这是我实测算出来的，不是估计。
- **收藏用的星星按钮只有 32×32 像素**，比苹果官方建议的最小可点击尺寸（44×44）小了不少，对手指稍大或者手不太稳的用户来说容易点不准。

考虑到你的目标是上架 App Store，这两条我会建议提前修，因为它们属于苹果审核时比较容易被挑出来的那类问题。

### 4. 应用里藏着不少"看起来在，其实点了没反应"的东西

举几个例子，方便你有画面感：
- 首页藏着一整套旧版的"随堂测验"界面，代码都还在，但已经没有任何按钮能进去，是彻底的死角落。
- Shadowing（跟读）功能里，AB 循环、跟读对比、难度分级这几个功能后台逻辑全部写完了，但按钮被藏起来了，用户完全用不到——等于做了一半的功能被"藏"起来而不是"完成"或"删除"。
- 删除单词这个功能，后端函数写好了，但界面上找不到任何一个能触发它的按钮。

这些东西不影响现在能不能用，但会让以后接手的人（包括我）越来越分不清哪些是真代码、哪些是死代码，维护成本会一直悄悄增加。

## 三、重点：关于你说的"多母语支持"

这是你现在最关心的问题，我要讲得仔细一点。

### 先说一个好消息：这件事你之前已经想过了，而且想对了

我们之前一起梳理产品方向的时候，已经确定了一套"四层架构"：

```
学习内容（Learning Content）
    ↑
母语支持（Native Language Support）   ← 你现在想做的事，就是这一层
    ↑
目标语言标准（Target Language Standard，比如"瑞典语"这套语法规则）
    ↑
学习引擎（Learning Engine，跟具体语言无关的学习逻辑）
```

也就是说，"让说英语、说西班牙语的人也能用 SpråkLab 学瑞典语"这件事，**在产品设计层面已经有了明确的位置，不是一个新方向，而是"我们说好要做、现在要落地"的事情**。这一层的核心原则我们之前也确认过：**母语支持不是简单的翻译，而是"学习路径的本地化"**——中文母语的人学瑞典语，和西班牙语母语的人学瑞典语，需要的解释、容易犯的错、需要提醒的地方是不一样的，不是把中文换成西班牙文这么简单。

### 但坏消息是：代码现在完全没有为这件事做准备

我把几个具体的坑列出来，这些是我从代码里实际查到的：

1. **数据库的词条表里，没有"这段解释是给哪个母语学习者看的"这个维度。** 现在存中文释义的字段就叫"chinese"，是写死的。以后要加英文释义、西班牙语释义，没地方放，只能每加一种母语就加一个新字段——这种做法加两三种母语还行，加多了就崩了。正确的做法应该是把"母语"变成一个可以灵活扩展的维度，而不是一个个字段名。

2. **更麻烦的是一个历史遗留的命名错误**：代码里现在有个字段叫"english"（英文），但实际存的内容是**瑞典语解释**，不是英文。这是早期开发时起错的名字，一直没人改。如果现在不趁早处理，等你真的要加"英文母语支持"的时候，这个字段名字会造成实实在在的混乱——"到底哪个才是真的给英语母语者看的解释？"

3. **用户设置里没有"我的母语是什么"这个概念**，也没有"当前正在学哪种语言"这个概念——这两个概念现在完全不存在于系统里，需要从头设计。

4. **界面本身用的语言（按钮文字、菜单文字这些"外壳"）现在是写死的瑞典语，而且还有一部分中文、英文混进去了，不统一**。等你真的支持多母语的时候，"界面外壳该用哪种语言显示"是一个需要先想清楚的问题——是所有母语的用户看到的界面外壳都一样（比如都用瑞典语或都用英语），还是外壳也要跟着用户的母语切换？这是一个产品决策，不是纯技术问题，我建议你来定。

### 我的建议：分几步走，不要一次性把所有语言都设计进去

按"先把架构定对，再往里加内容"的原则（这也是你之前确认过的"规范优先"原则），我的建议是：

1. **第一步：先把"母语支持"这一层的数据结构定义清楚。** 核心是想明白"哪些知识是跟母语完全无关的瑞典语本身的东西（词汇、语法这些）"，"哪些是需要针对某个母语学习者单独准备的内容（翻译、对比讲解、常见错误提醒）"——这两类东西要在数据库层面分开，而不是像现在这样混在一起。

2. **第二步：顺手把那个"english"字段名字的历史遗留问题解决掉。** 这个不解决，会一直是个雷，越往后处理成本越高。

3. **第三步：先只做一种新母语（比如英语），把整条链路跑通**——从数据库结构、内容如何准备、界面怎么切换，全部验证一遍，确认设计是对的。**不建议一次性把中文、英文、西班牙语等好几种母语的字段和界面都设计出来**，那样风险更高、也更难验证对错。跑通一种之后，加第二种、第三种母语的成本应该会明显降低，这也是这套架构设计本来的意义所在。

4. 界面外壳该用什么语言显示、要不要跟着母语切换——这个决策建议尽早定下来，因为它会影响接口怎么设计。

## 四、跟"多母语支持"很像但其实是另一件事：以后支持更多目标语言

你提到"稳定后还可能增加其他的语言学习"——这里要提醒一下，这和"多母语支持"是**两件不同的事**，很容易混在一起说：

- **母语支持** = 还是学瑞典语，但服务不同母语背景的人（中文母语、英文母语……）
- **目标语言标准** = 不止学瑞典语了，以后还要能学英语、日语这些**新的"要学的语言"**

现在代码里，"瑞典语的名词怎么变格、动词怎么变位、怎么分词"这些规则是直接写死混在通用业务逻辑里的，没有独立成一块。以后如果真要加日语，日语的语法规则、分词方式跟瑞典语完全是两码事，现在这种写法没法直接复用，需要重新设计这一层。

**我的建议：这件事现在不用动。** 你眼下真正要做的是"母语支持"，不是"新增目标语言"。但建议你在做母语支持那部分的数据结构改造时，顺手把"这是瑞典语专属的规则"和"这是任何语言都通用的学习逻辑"这两类东西分清楚——这样等你真的要加新的目标语言时，不用把母语支持这部分推倒重来。

## 五、如果只让我给一个"先做什么"的答案

按我的判断排一个先后顺序，供你参考和调整：

1. **先修同步失败无提示的问题。** 改动范围不大，风险最低，但直接关系到用户信不信任这个产品真的帮他记住了学习进度。
2. **定下母语支持的数据结构方案，顺手把 english 字段命名的历史问题解决掉。** 这是你现在最想推进的方向，越早定型越好。
3. **定下底部导航要不要扩容**（还是 3 个标签，还是加到 4-5 个）——因为后面每加一个新模块都会撞上这堵墙，越晚决定成本越高。
4. 统一字号/间距/颜色、清理死代码这些，可以按自己的节奏慢慢来，不会卡住你现在最想推进的多语言支持工作。

## 六、请你确认：我们的理解是否一致

这几点决定了下一步怎么写正式的规范文档，麻烦你确认一下，或者直接告诉我哪里不对：

1. 你说的"多母语支持"，是指以后要让说英语、西班牙语等其他语言的人，也能通过 SpråkLab 学瑞典语——这个理解对吗？
2. 界面本身现在是中文，以后要不要保留中文界面？还是以后要变成"界面语言跟着用户的母语走"（比如英语母语的人看到的是英文界面）？
3. 近期的目标就是"母语支持"，"支持更多目标语言（不只是瑞典语）"是更远期以后再说的事——这个理解对吗？
4. 是否同意"先用一种新母语（比如英语）把整条链路跑通、验证设计没问题，再推广到更多母语"这个节奏，而不是一次性把所有语言都设计进去？

等你确认这几点之后，我可以基于此，把"母语支持"这一层的具体数据结构方案和落地步骤写成一份正式的规范草案，供你审核。
